# v1.2: verified point-cache reuse

Status: **PASS for the exercised correctness checkpoint; production release INCOMPLETE**.
Fresh evidence includes 75 top-level checks / 43 CTest, five TSAN, four ASan/UBSan,
34 Node / 134 Python / 30 Java units, live authenticated SDK document/media recovery
and a fresh 1M dirty restart with 45 changed records, five deletions and five
filtered exact-score checks. The complete paired benchmark has finished; exact, ANN, ingestion, filtering,
availability and recovery results are reported separately below.
This is an implementation decision within the existing request to improve native
search while preserving correctness, durability and compatibility.

## Motivation and alternatives

The qualified `ac9f879...` candidate forces an ID-cache invalidation before each
native search candidate fetch, including up to 40 fetches for ANN top-10. Its
completed 10K warm-query phase measured ANN p50 8.427 ms versus pgvector 0.710 ms.
Those are retained phase results, not a complete benchmark or a cache-speed claim.

| Approach | Tradeoff |
| --- | --- |
| Keep forced storage rereads | Conservative, but repeated candidate materialization and SST seeks remain |
| Reuse the existing ID cache only with a validated source certificate | Chosen: keep authoritative checks while eliminating repeated reads of unchanged rows; conservative invalidation and a small memory cost |
| Add a separate vector payload cache | Duplicates ownership, accounting and invalidation infrastructure; unnecessary here |

## Invariants and proposed integration

Authoritative WAL/LSM bytes, Raft acknowledgement, precision, tenant checks, source
eligibility and final search certificates remain unchanged. A cached full JSON row
is eligible for authoritative point lookup only when a previous complete storage
read published it with the same root/collection mutation certificate. Writer-fed
entries have no such proof. A source change, missing proof or recovery invalidation
requires the full memory/SST version-resolution path. No new persistent format,
transaction system, replica state or result-set cache is introduced.

Store the optional proof in the existing striped ID-cache entry. Cache publication
keeps the existing collection-lock/certificate guard and atomically installs the
row and proof under the existing stripe lock. Full point reads retain a stable SST
file set under the existing collection read lock, matching ordinary point reads.
Native search may then omit its forced invalidations; per-row authorization,
float64 score recomputation and final index/source validation still run.

The proof is four uint64 values plus optional storage, approximately 40 additional
bytes per cache entry on this build (about 1.9 MiB at 50000 entries per collection,
before allocator/alignment effects). Existing entry caps/eviction and memory-pressure
controls apply. No extra global cache or global query lock is added. Any collection
mutation conservatively invalidates proofs, even for unchanged IDs.

## Evidence and remaining gates

The pre-fix storage test reproduced trusting an older writer-fed cache entry over a
newer SST row. The corrected test passes newer-row/tombstone resolution, warm reuse,
mutation, restore, drop/recreate and namespace checks; all prior 18 point-read
interleavings also pass. Native integration preserves exact IDs/scores, ANN results,
hybrid filters and stale-index rejection while exercising actual verified reuse.
The native fixture originally changed the catalog between queries and incorrectly
assumed a fixed overfetch count; those failed attempts remain retained. Tests now
respect existing catalog eligibility and validate every candidate actually fetched.

An isolated pre-change profile over 4096 stable 25D rows measured a median 3.84 ms
for 40 forced lookups versus 0.20 ms for cached lookups (200 iterations). This is a
point-lookup microprofile, not an ANN speedup or PostgreSQL comparison.
Raw evidence: `docs/v1.2-evidence/verified-point-cache-20261101/`.

Native exact/ANN `search` metadata now includes `payload_fetches` and
`payload_cache_hits`. These count verified record reuse; every query still ranks
vectors, checks authorization and validates its final source/index certificate.

## Checkpoint implementation and compatibility report

**Implementation — PASS for the exercised scope.** `engine/src/lsm.cpp` changes
only the existing striped ID-cache entry and authoritative point-read path:
`upsertIdIndex`, `lookupIdIndex`, `publishPointReadCache`, and
`findStrongSnapshotBound`. `engine/src/database_engine_vector_native.cpp` removes
forced eviction for exact winners, ANN candidates and hybrid payload retrieval;
incremental maintenance resolution keeps its explicit invalidation. Search
metadata adds `payload_cache_hits` (and ANN `payload_fetches`) without changing
existing required request fields, scores, storage bytes or acknowledgements.
New tests are `lsm_verified_point_cache_test.cpp` and
`native_vector_point_cache_test.cpp`; CMake and the checkpoint runner include them.

**Testing — PASS for the recorded revision.** The full runner passed 75 top-level
checks including 43 CTest cases, document/media/authentication, RF3/partition,
request isolation, schema/incremental operations and dedicated crash failpoints.
Five targeted TSAN and four ASan/UBSan tests passed. Node 34, Python 134 and Java
30 unit tests passed; live Python/Java authenticated TCP/TLS and SIGKILL tests
verified 160 documents and 700000 media bytes per client. Raw attempts and binary
hashes are retained. No tests were disabled or changed to bypass a runtime failure.

**Performance — FAIL against the requested overall PostgreSQL parity target.**
The complete 10K/100K/1M public comparison and four 10K dimensional/metric
supplements passed their functional/reference acceptance checks. At 1M, exact
p50 was 49.73 ms versus PostgreSQL 112.23 ms, but ANN was 18.24 ms versus 2.26 ms,
ingestion 2548 versus 23505 rows/s, and 1% filtered exact 7031.49 versus 76.90 ms.
Strict mixed ANN reads succeeded on 26/360 attempts versus 360/360. Static held-out
Recall@10 was 0.9778 versus 0.9897. These are warm-cache, revision-scoped results,
not general superiority claims. Verified row-cache hits reached only about 5%
in the later 1M rounds; the microprofile does not establish an end-to-end causal
speedup. Source/archive/binary hashes match all 429 frozen source files.

**Reliability — PASS only for the tested failure model.** A fresh 1M fixture
verified 360 reads after acknowledged concurrent own-key writes, all 45 surviving
changed vectors, five deleted IDs, the 999995-row count and five filtered exact
searches after SIGKILL/restart. The disposable dirty root was preserved before
recovery. Snapshot/drop/recreate, tenant namespace, stale writer/replay cache and
tombstone behavior pass targeted checks. Process crash is not physical power loss.

**Release — INCOMPLETE.** Strict ANN availability under concurrent mutation,
sustained production qualification, upgrades/platform packaging and external
security/release gates are not passed by this cache checkpoint. Complete distributed
vector search remains outside the gated standalone Community contract. No commit,
push, publication or deployment has been performed.

## Final recovery observation

The main paired 1M crash/restart verified all 45 surviving changed vectors, five
deletions and the 999995-row count. Connection readiness took 99.04 s; ANN then
required explicit reconstruction taking 2158.07 s (35.97 min). Ten post-rebuild
queries achieved Recall@10 0.96 against a new independent reference, satisfying
the declared 0.95 recovery check. This small recovery sample is separate from
the 1000-query static held-out set. PostgreSQL became connectable in 0.615 s,
retained its index and achieved 0.99 on the ten recovery queries. Both initial
build and restart costs are operational limitations, not excluded overhead.
