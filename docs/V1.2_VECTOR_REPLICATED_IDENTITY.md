# Replicated identity prerequisite for vector indexes

Status: INCOMPLETE for full distributed vector operations. This follows the
[verified freshness/catalog checkpoint](V1.2_VECTOR_FRESHNESS_AND_CATALOG.md).
Public ANN and the distributed catalog remain gated.

## Implementation and compatibility

The current collection `id` is generated independently on each replica and is
already exposed through existing document/media APIs. Changing it would create an
unnecessary compatibility risk. It is preserved.

Committed CREATE_COLLECTION apply now passes the common Raft log index to an
internal creation helper. Newly created metadata gains an additive
`vector_incarnation: "raft-create:<index>"`. All replicas applying that committed
creation derive the same value. A later drop/recreate receives a new creation
index and therefore a new incarnation. No new consensus operation or authoritative
record store was added, and no existing Raft entry field is required from clients.

`DatabaseEngine::createCollection` retains its existing public C++ signature and
symbol. Its wrapper uses the existing behavior for standalone/internal creation.
The existing metadata write adds the optional field; it does not perform a second
metadata write. Existing collection IDs, document/vector bytes, media paths, WAL
format and acknowledgement configuration remain unchanged.

Replaying a duplicate CREATE_COLLECTION does not replace an existing incarnation
or assign a guessed identity to a legacy namespace. The new helper is private to
the engine. Legacy namespaces therefore still require an explicit, compatible
migration design; old IDs are not silently changed.

## Remaining distributed gates

This field solves identity for newly committed creations on updated replicas; it
does not implement a mixed-version capability handshake, legacy incarnation
migration, durable public index operations, graph memory admission, distributed
fan-out or actual shard data transfer. The internal catalog continues to reject
RF3 explicitly until those eligibility and compatibility rules are integrated.

An old replica can ignore this additional metadata behavior, so graph/catalog
eligibility must not be inferred from the leader's local field alone. No
mixed-version vector-readiness claim is made.

No new performance result is claimed for this metadata-only creation change. The
paired write-path replay in the preceding report measured the preceding source
checkpoint and is not relabeled as a measurement of this revision.
