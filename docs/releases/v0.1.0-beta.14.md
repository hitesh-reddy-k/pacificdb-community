# PacificDB Community v0.1.0-beta.14

Beta.14 removes a major Node.js transport bottleneck and exposes PacificDB's
batched storage path through the public SDK.

## What improved

- The Node.js client now reuses a bounded persistent TCP/TLS connection pool
  instead of opening and closing one socket for every request. The default pool
  limit is 16 and applications can configure any value from 1 through 32.
- `await client.connect()` prewarms the configured pool for latency-sensitive
  workloads. `client.close()` rejects queued work and closes every socket cleanly.
- Dropped or expired sockets reconnect when their pool slot is used again.
  Mutating requests are never automatically replayed after an ambiguous network
  failure, preventing accidental duplicate writes.
- The Node.js SDK now provides `insertMany(collection, documents)` and sends the
  documented `{ "action": "insertMany", "collection": ..., "data": [...] }`
  protocol in one request.
- The engine accepts the new `data` field while retaining the older `documents`
  field for compatibility. A batch uses the existing `DatabaseEngine::insertMany`
  and `LSM::putMany` path, including one grouped WAL append.
- End-to-end coverage now exercises persistent connections, a 500-document
  batch, authentication, media and vector operations, graceful restart, abrupt
  restart, and post-restart batch durability.
- A reproducible, count-verified PacificDB-versus-MongoDB ingestion benchmark is
  included under `benchmarks/insert-many`.

## Node.js example

```js
import { PacificDBClient } from '@pacificdb/client';

const db = new PacificDBClient({
  host: '127.0.0.1',
  port: 9000,
  database: 'app',
  poolSize: 16
});

await db.connect();
const result = await db.insertMany('users', [
  { id: '1', name: 'Ada' },
  { id: '2', name: 'Grace' }
]);
console.log(result.inserted);
db.close();
```

Persistent connections consume engine connection-worker capacity. Deployments
with multiple application processes should size `CONN_MAX_THREADS` and
`MAX_CONNECTIONS` for the aggregate number of active client pool sockets.

## Measured batch-ingestion result

The release benchmark used the same Linux host and ext4 device for both engines,
50,000 measured documents after a 5,000-document warmup, batches of 500, four
concurrent producers, a pool limit of 16, and five alternating samples. Both
engines waited for durable storage: PacificDB used WAL fsync and MongoDB 8.3.8
used write concern `{ w: 1, j: true }`.

| Engine | Median records/sec | Median batch p50 | Median batch p95 |
| --- | ---: | ---: | ---: |
| PacificDB beta.14 | 3,135 | 450.6 ms | 1,432.5 ms |
| MongoDB 8.3.8 | 7,298 | 185.4 ms | 869.4 ms |

PacificDB delivered 43% of MongoDB's sustained durable batch throughput in this
run; MongoDB was 2.33x faster. The original projected 33,000 records/sec was not
reproduced and is not claimed by this release. Profiling identified PacificDB's
WAL append/fsync path as the main remaining ingestion bottleneck.

See the [complete benchmark methodology and raw samples](https://github.com/hitesh-reddy-k/pacificdb-community/blob/v0.1.0-beta.14/docs/benchmarks/2026-09-16-insert-many.md).
