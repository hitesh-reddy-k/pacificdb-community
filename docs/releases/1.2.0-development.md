## Implemented checkpoint: bounded exact ranking

`queryVector` accepts the additive `search_mode` option:

```json
{"action":"queryVector","collection":"embeddings","vector":[0.25,0.75],
 "metric":"cosine","k":10,"search_mode":"exact","filter":{"category":"news"}}
```

Node:

```js
await db.queryVector('embeddings', [0.25, 0.75], {
  k: 10, metric: 'cosine', searchMode: 'exact', filter: { category: 'news' }
});
```

Python/Java raw vector operations accept `search_mode` in their existing option
maps. `exact` always executes exact search. `auto` uses exact fallback by default;
`VECTOR_HNSW_ENABLED` and `VECTOR_HNSW_ALLOW_FALLBACK` only influence its fallback
default, and cannot enable a builder. Explicit `ann` requires a qualified READY
index. Without an explicitly selected eligible preview index it returns
`vector_index_unavailable: ABSENT`.
Set wire `allow_exact_fallback: true` (Node `allowExactFallback: true`) to permit
exact fallback. Explicit false rejects fallback for auto or ann. Successful replies
add `search` with requested/executed mode, index state and fallback status.
No supported mode invokes the removed quadratic builder. With
`PACIFICDB_VECTOR_PREVIEW_ENABLED=1`, standalone clients can explicitly create and
select a native index. See [public lifecycle and hybrid API examples](../V1.2_NATIVE_VECTOR_PREVIEW.md)
and [schemas and incremental maintenance](../V1.2_SCHEMAS_AND_INCREMENTAL_ANN.md).
This opt-in preview does not enable clustered vector catalog/schema operations.

See the [safety/concurrency checkpoint report](../V1.2_VECTOR_CHECKPOINT_1_SAFETY.md)
for request scopes, compatibility changes and reproducible evidence.

Exact ranking retains at most K candidates, with only competitive rows materialized
while their iterator views are valid. Scores preserve legacy double precision:
cosine similarity, dot product, or negative Euclidean distance. Higher is better.
Equal scores use ascending string ID. Mismatched dimensions retain legacy skip
behavior in schema-less collections. Configured collections additionally enforce
their creation-time vector schema on mutations and replay. Full document results
with `score` remain compatible. Candidate materialization is bounded in retained
count, not necessarily in total work: adversarial ordering can replace every candidate.

The shared row-tenant and read-context visibility checks now run in vector search.
The server scopes read context to a request with cleanup on error. Existing Raft
strong-read fencing remains in place. This does not add historical MVCC snapshots
or distributed shard fan-out.

### Explicit resource failures

- `k > MAX_RESULT_DOCS`: reject rather than cap silently.
- `MAX_SCAN_ROWS` exhausted: `vector_scan_limit_exceeded`; no prefix ranking returned.
- Cancellation/deadline token: `vector_query_cancelled`; no successful partial exact answer.
- Configured query time limit: `vector_query_timeout`, checked without requiring
  a worker cancellation token.
- Retained serialized candidate documents exceed existing result-byte budget:
  `vector_candidate_bytes_exceeded`.
- Final output (including scores) also undergoes the existing result-byte check.

These are intentional correctness changes for previously partial/ambiguous vector
answers. Callers must handle errors and explicitly raise administrator budgets if
needed. The result byte budget is a serialized payload budget, not a hard RSS quota.
The shared storage iterator may retain memory snapshots and locks independently.

## Validation and reproduction

Build a separate candidate directory (never reuse an unknown old CMake cache):

```sh
cmake -S engine -B build-v1.2 -DCMAKE_BUILD_TYPE=Release \
  -DPACIFICDB_ENGINE_VERSION=1.2.0-dev
cmake --build build-v1.2 -j2
ctest --test-dir build-v1.2 --output-on-failure
build-v1.2/db_engine_vector_exact_test
VECTOR_HNSW_ENABLED=false build-v1.2/db_engine_vector_correctness_test
node scripts/test-community-e2e.mjs build-v1.2
node scripts/test-p0-media.mjs build-v1.2
node scripts/test-engine-auth-boundaries.mjs build-v1.2
node scripts/test-community-rf3.mjs build-v1.2
```

For the `1.2.0-dev` build, run the E2E command with
`PACIFICDB_EXPECTED_ENGINE_VERSION=1.2.0-dev`; it defaults to the released `1.1.2`
and verifies the exact expected shell banner. Media crash tests require a separate
build configured with `-DPACIFICDB_ENABLE_TEST_FAILPOINTS=ON`. Do not run destructive
failpoints on production data or interpret a production binary's disabled failpoint
as a successful crash test.

The complete existing regression entry point is `scripts/test-community.sh`.
It hardcodes released version checks, so it is not itself a v1.2 release pipeline.
Use its individual suites with the development build; do not disable failing tests
or silently change release assertions to claim qualification.

A reproducible checkpoint runner records each native test, CTest and exercised
API/media/auth/RF3 suite with logs and timeouts:

```sh
python3 scripts/test-vector-checkpoint.py --build build-v1.2 \
  --failpoint-build build-v1.2-failpoints --expected-version 1.2.0-dev \
  --evidence /tmp/v12-checkpoint-new-attempt
```

The evidence directory must be empty. Missing tools/binaries are BLOCKED; failed
assertions remain FAIL. Omitting the failpoint build leaves the checkpoint
INCOMPLETE. Even a PASS means this checkpoint's exercised checks passed, not that
the full v1.2 release or production acceptance is complete.

`engine/tools/vector_exact_benchmark.cpp` can be compiled against the unchanged
baseline and candidate core with identical compiler/durability settings. It creates
an owned disposable root, inserts deterministic normalized float32-valued JSON
vectors in 500-row batches, validates count, flushes, warms twice, and measures
exact queries. It is an in-process microbenchmark, not a replacement for the
external held-out GloVe case study or a client-observed pgvector comparison.

```sh
WAL_FSYNC_ENABLED=true WAL_FLUSH_ON_COMMIT=true VECTOR_HNSW_ENABLED=false \
  build-v1.2/db_engine_vector_exact_benchmark 10000 10 25
```

Run baseline and candidate sequentially. Preserve full logs and `/usr/bin/time -v`
output. Peak process RSS includes ingestion and setup. Percentiles p95/p99 are
omitted below 1,000 measured requests. No ingestion improvement is claimed from
this search change. Validation outcomes are recorded in [the checkpoint report](../V1.2_VECTOR_VALIDATION.md).

## Native service and hybrid development checkpoint (2026-10-30)

The trusted C++ integration now has a bounded shared index registry, source-memory
reservations, cancellation/deadlines, authoritative candidate revalidation and
composite vector/lexical generation publication. A real derived BM25 inverted index
and ranked RRF hybrid retrieval are implemented and tested internally. Existing
public query modes remain safely gated; these additions are not public production
ANN or distributed retrieval qualification.

Mixed document/media/vector traffic exposed two secondary-index defects: rebuild
lock inversion and delayed queued payloads resurrecting deleted entries. Rebuild and
batch maintenance now use collection-before-index locking; pending IDs resolve the
latest authoritative versions before application. Same-collection writes may wait
through a rebuild; indexed batch maintenance adds point-read I/O. WAL durability and
formats are preserved. Normal and ThreadSanitizer mixed tests pass, and the current
normal CTest suite passes 33/33. The broader post-repair checkpoint passed 62 top-level checks.

See the [implementation, test evidence and qualification boundaries](../V1.2_NATIVE_SERVICE_AND_HYBRID.md)
for actual scope, raw failures and scale diagnostics. The release remains INCOMPLETE.


## Native standalone vector API preview (unreleased)

An opt-in standalone lifecycle API now connects durable definitions to background
flat float64 exact and HNSW dense indexes, plus BM25/RRF hybrid retrieval. Existing
queries keep their storage scan behavior unless a named index is requested.
Freshness errors remain explicit, with policy-controlled exact fallback. Node,
Python and Java expose named lifecycle/hybrid methods. Global invalid query
timeouts are rejected before recovery; per-request vector deadlines are supported.
Collection drops cancel derived workers without joining them in committed apply.

## ANN construction and restart behavior

ANN is optional for durable vector storage and exact search. Starting an empty
database does not require constructing a million-vector graph. Creating an ANN
index over existing committed records performs a background build; searches and
client connections do not trigger repeated full construction. Supported dense
HNSW indexes use incremental maintenance only when explicitly configured, with
bounded history and manual rebuild requirements. This is not universal automatic
maintenance across index types.

The current preview persists vectors and index definitions, not the graph. After
process restart, ANN starts ABSENT and requires explicit rebuilding. Exact fallback
is available only under its documented policy/resource limits. In the latest 1M
GloVe-25 comparison, initial ANN build took 45.82 min and post-crash reconstruction
35.97 min; live records were recoverable before ANN readiness. Persisted checkpoints
and replay are proposed future work, not implemented functionality.

See the [completed self-run benchmark](../v1.2-evidence/community-verified-cache-comparison-20261101/REPORT.md)
for latency, recall, ingestion, filtering, memory, availability and recovery costs.
The complete production release remains INCOMPLETE.
