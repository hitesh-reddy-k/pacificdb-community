# PacificDB Community 1.1.2 — security and reliability patch

Published: 7 October 2026. **Prerelease.**

[GitHub release](https://github.com/hitesh-reddy-k/pacificdb-community/releases/tag/1.1.2), tag `1.1.2`,
source revision `07ffb00a7b224c5ca5cd338c2b0b86723c3b7721`.
Linux native/Workbench packages, npm tarballs, Python wheel and Java JARs are
published with verified SHA-256 digests. Registry publication and final
Windows/macOS installers remain unavailable. Stable promotion is still gated.

This is the open-source, self-hosted Community edition. Engine, native/npm CLI,
Node.js/Python/Java SDKs, Workbench and Helm source versions are aligned at
1.1.2. No billing, subscription limits or commercial control plane is
added. Do not mistake previously published 1.1.1 installers or registry packages
for this security patch.

## Security fixes

The patch addresses the nine findings in the internal review of revision
`89735a9b6467094e0b9a679b9812ad514284e223`, with focused regression coverage:

| Finding | Change |
| --- | --- |
| Media authorization trusted caller-supplied database | Resolve the stored manifest and authorize its actual owning database for reads, chunks, resume, cleanup and deletion. |
| Managed Raft listener exposed on all interfaces | Managed desktop/npm/native local launchers bind both listeners to loopback; invalid bind addresses fail closed. |
| Untrusted Raft lengths allocated before validation | Reject zero/oversized frames before allocation; sender/receiver share the existing payload ceiling. |
| Caller-selected `userId` crossed storage namespaces | Authorize the actual `(userId, database)` tuple through owner/grant metadata and effective principal/role checks, including nested bulk requests. |
| Validated and effective binds used different stores | Use resolved configuration consistently for security validation, binding and startup reporting. |
| Sparse manifests caused effectively unbounded loops | Enumerate actual stored chunks in bounded pages rather than scan declared chunk counts. |
| Node responses grew without a byte limit | Count raw bytes before decoding/appending; retire oversized-response connections without automatically replaying writes. |
| A new login attempt cleared account lockout | Persist lockout expiry and enforce it across attempts and restart; legacy locks require an explicit reset. |
| Backtracking regex could outlive query deadlines | Use RE2, bounded patterns and explicit rejection of unsupported syntax/options. |

Further authorization review fixes cover request aliases, unscoped/internal
catalog access, action permission mapping and API-key role ceilings. Internal
OWASP-mapped checks also identified audit gaps: denied and failed actions now
retain actor/scope attribution; audit append/archive failure and buffer loss
are observable, with recovery events. These are scoped internal checks, not
an OWASP certificate or exhaustive penetration test.

## Ownership and administration

- With authentication enabled, the creator owns the new database. Other users
  require an explicit read-only, read-write or co-owner grant.
- `system` is a storage namespace, not a public-access permission. Namespace
  names and matching database names never bypass authorization.
- Owners can manage grants and transfer ownership. Final-owner removal is
  rejected. Grants and ownership do not elevate the account/API-key role.
- The installation operator provisions the engine superadmin explicitly;
  database creation does not automatically make someone superadmin. There is
  no built-in shared production credential. Recovery overrides are audited.
- Existing authenticated databases without ownership metadata remain
  unassigned and are accessible only to superadmin until explicitly assigned.
- Metrics-only API keys preserve their role across reload. They can view
  security metrics, but cannot read documents, write data or administer the
  engine.

## Desktop, durability and packaging

- Preserve sandboxed renderer isolation, restricted navigation, private
  loopback bridge, request limits and secret redaction.
- Exercise bundled-CLI backups/verification, restore history, CRUD/media,
  graceful shutdown, restart persistence and caller-owned data preservation.
- Add source-revision and native-binary SHA-256 manifests; packaging refuses a
  release engine that does not match the clean source revision. Runtime tests
  inspect both identity and hashes and reject reviewed build tools in ASAR.
- Keep source, installer, signing and external qualification distinct. Actual
  Debian/NSIS/DMG lifecycle gates remain in release workflows; no missing gate
  is converted to PASS.
- Retain post-1.1.1 bounded log-descriptor diagnostics, descriptor-cleanup and
  native lifecycle stream-drain fixes.
- Storage format and Raft protocol version stay at 2. This does not waive
  backup/restore or mixed-version qualification requirements.

## Deployment and audit alerts

- Digest-pin the container base; retain non-root, read-only-root, capability,
  seccomp, TLS/mTLS, RF3/quorum and allowlisted-network deployment controls.
- Probe actual pod IPs with verified mTLS, a bounded JSON reply and explicit
  deadline. Per-pod metrics-only credentials are required because key stores
  are node-local.
- Readiness rejects unavailable, disabled or unhealthy audit logging. Liveness
  remains responsive during audit failure to avoid a restart loop.
- Supply a restricted monitor service/timer, private configuration and
  credential files, remote HTTPS enforcement, redirect rejection, delivery
  failure/staleness metrics and alert runbooks.
- Verify the complete local engine → monitor → pinned Alertmanager → receiver
  path: failed audit append, firing notification, receiver rejection/retry,
  actual successful receipt, audit recovery and resolved notification.
  Alertmanager API acceptance alone is not operator delivery proof.

## Dependency risk acceptance

The retained runtime npm audit reports zero advisories. Eight moderate
build-only package entries trace to the reviewed `sprintf-js` advisory. They
are **accepted, not fixed**, under an exact-version exception expiring
**6 November 2026 at 00:00 UTC**. CI rejects new/runtime/unreviewed/expired
findings. Build tools are excluded from application runtime code; privileged
release builds must not process untrusted code/logging.

See [the acceptance policy](../security/BUILD_TOOL_ADVISORY_ACCEPTANCE.md).
This is not a complete native, JVM, Python or container vulnerability audit.

## Upgrade requirements

1. Make and verify an external backup and an offline copy of the data root.
   Keep the previous binaries; test restore and the patch against a disposable
   copy before replacing a real deployment. Never run incompatible engines
   concurrently on one data directory.
2. Build/install matching 1.1.2 components. RE2 development/runtime libraries
   are now required; Debian/Ubuntu source builds need `libre2-dev` in addition
   to OpenSSL and LZ4 development libraries.
3. In authenticated deployments, provision/recover the operator superadmin,
   list unassigned databases with `security_database_unassigned_list`, then
   use `security_database_owner_assign` to assign an existing principal to the
   intended database. Review ACLs before reconnecting ordinary users.
4. Review regex filters: RE2 does not accept backreferences/lookarounds.
   Unsupported syntax/options produce an explicit invalid-query error.
5. Provision certificates and per-node metrics tokens, verify readiness and
   audit delivery, and exercise rollback/restore. Keep credentials out of
   source control, command-line arguments and public reports.

## Production-readiness statement

**Maintainer-reported:** the maintainer states that verification is complete.
That statement is recorded as an attestation, not independently validated
release evidence. This patch is designed for self-hosted production operation
with the documented security and backup safeguards; it is not an unconditional
certificate that every installation is safe for real data.

**Retained repository evidence:** focused security regressions, Linux
sandboxed package runtime checks, exact binary identity/hash checks, a
non-root/read-only container smoke, Helm/schema validation, zero runtime npm
advisories, and actual local audit-alert failure/retry/recovery receipts passed
on their stated candidate revisions. The latest pre-version-alignment hardening
candidate was `0e7320f63e0831699429d8613861c4825277b101`.

**Historical endurance/durability:** the eight-hour run at revision `89735a9`
recorded 28,802 seconds, 84,623 operations and zero errors; physical recovery
evidence for the same revision records three passing cuts. Those results are
not rewritten as exact-1.1.2 evidence. No eight-hour test was restarted.

**Not established by the available evidence:** an independent external review
signed for the final release revision/artifact digests, actual production
cluster/network/encrypted-storage and operator notification proof, and final
signed/notarized Windows/macOS installers. An unsigned exception from 1.1.1
does not apply to 1.1.2.

Before storing real data, the operator must validate the deployment, verify
backups/restores, enforce authentication/TLS and least privilege, maintain
monitoring, and accept the documented residual risks. No database or security
review guarantees absence of vulnerabilities, outages or data loss.

Provide the external reports and exact artifact identities to the existing
[independent-review validator](../SECURITY_REVIEW.md) and
[release qualification process](../RELEASE_EVIDENCE.md). Stable release promotion and
broader certification remain gated; this document does not bypass them.
