## Changes

- Secondary metadata-index rebuilds stream selected fields from resolved committed
  records into verified segments instead of retaining every complete document.
  Encoded mutation chunks default to 1 MiB, configured by
  `COLUMN_INDEX_BUILD_BATCH_BYTES` (4 KiB–16 MiB). A single supported oversized
  scalar is written alone rather than truncated. This is a chunk target, not a
  strict total RSS limit. Existing collection-before-index locking remains.
- A private directory receives a complete generation; segment readback precedes
  publication, derived caches are invalidated before READY, and catalog writes
  synchronize their file and parent. Interrupted/failed definitions rebuild on
  replay. Authoritative records and persistent formats are unchanged.
- Recovery-index construction selects the newest eligible version, preserving an
  older committed record beneath a pending replacement. A real abrupt-process
  WAL regression verifies indexed/document parity across two restarts.
- SST point reads and merged iteration resolve all versions of an ID, including
  duplicates crossing blocks. Highest version wins; later row/file wins ties;
  active memory wins equal-version storage-layer ties. Visibility is resolved
  before choosing winners, so flushing a pending replacement does not hide the
  existing committed record. Tombstones and traversal cancellation are covered.
- Shared native file operations reuse the manifest's Windows file-flush and
  write-through replacement behavior for SST/index publication. Windows has no
  documented POSIX directory-fsync equivalent; Linux results do not certify
  Windows or physical-power behavior.
- The release operations gate now supplies the validator's required document and
  alert inputs. The actual gate failed before the change and passed afterward.
- Native Linux, Windows and macOS Intel/ARM package jobs now run the four new
  filesystem/SST/index/recovery tests before packaging.

Primary implementation: `engine/src/lsm.cpp`, `engine/src/storage_format_v2.cpp`,
`engine/src/durable_file_ops.cpp`, `engine/src/lsm_manifest.cpp`; targeted test
files are committed alongside them. No WAL durability setting, acknowledgement
policy, storage format, network protocol or SDK signature was weakened.

## Matched 1M metadata-index diagnostic

Same GloVe25 dataset with 999,995 surviving rows, 45 acknowledged updates and
five deletions from the earlier recovered fixture. Disposable destinations are
initialized by the engine; offline data restoration preserves each destination's
new ownership identity. Original fixture data are not modified. Baseline and
candidate run sequentially with four server/two client logical CPUs, WAL/fsync
unchanged and the same request timeout. This is one build per runtime on one
Linux x64 host, not a throughput or tail-latency qualification.

| Measurement | Frozen prior executable | Candidate |
| --- | ---: | ---: |
| Create-index request | 15.026 s, ambiguous acknowledgement | 7.593 s, successful acknowledgement |
| First observed READY | 30.311 s | 7.594 s |
| Peak sampled process PSS, entire trial | 5471.39 MiB | 268.64 MiB |
| Post-publication SIGKILL/restart | 117.020 s | 63.581 s |
| Post-restart OR-filter exact median, five measured queries | 4602.73 ms | 7180.76 ms |

The baseline's ambiguous write result remains a **FAIL**; eventual READY does not
turn it into a passing acknowledgement. The candidate returned successful ACK
and complete READY. Both physical index audits independently checked all
999,995 IDs/values with checksummed decoding, and both restarts verified the
45 updated records and five tombstones. Seven filtered exact calls per runtime
(two warmups/five measured) matched independent strict and tie-aware ground truth.
No meaningful p95/p99 conclusion is drawn from five measured queries. No new
PostgreSQL/pgvector, Qdrant, ANN-throughput or media-efficiency trial is claimed.

The shared filtered-scan sample regressed from 4.60 s to 7.18 s. Correctness
passed, but removing that measured regression is unfinished performance work;
the aggregate diagnostic PASS does not qualify latency.

The builder remains synchronous and source-locked; target-collection writes can
wait during construction. These measurements do not certify a universal build
latency, unrelated-write impact, hard allocator budget or arbitrary-scale load.
