# ANN commit visibility follow-up (unreleased)

This change removes unnecessary incremental ANN invalidation when unrelated
documents or media advance the global Raft commit index. It does not increase
the default freshness wait, enable exact fallback, or change authoritative data,
WAL acknowledgements, storage format, replication format, or SDK requests.

A smaller regression now reproduces an unnecessary `STALE` error on that previous

that arbitrary host exhaustion is harmless.

## Eligibility rules

Only the native incremental HNSW integration opts into complete visibility:

- Its authoritative source scan rejects pending or not-yet-visible records.
- Every committed source mutation is covered by the existing bounded journal;
  visibility floors, gaps and resets remain explicit eligibility barriers.
- The observed Raft commit must already have reached the applied watermark.
- Root, collection and index-configuration revisions must match exactly.
- Global visibility may advance only monotonically, and the journal head must
  still equal the generation's covered cursor at acquisition and final validation.
- Actual source changes still require maintenance and bounded request retries.

Manual HNSW, exact flat and other uncertified generations retain strict certificate
equality. The general certificate equality operator is unchanged. Hash collisions
in the bounded collection-revision table remain conservative invalidations.

Generation policy is published with a new metadata object sharing graph ownership;
queries do not copy the graph. Incremental graph edits still use the existing
per-index lock. This is not an implementation of immutable graph snapshots or a
new concurrent graph algorithm. Index rebuilds retain their existing readiness
and resource-budget policies.

## Background construction and status follow-up

The first fix applied only to completed incremental indexes. A controlled
publication pause then reproduced an unnecessary `STALE` result during initial
construction on commit `953c399`: an unrelated document commit invalidated the
finished graph. Complete incremental builds now accept monotonic global commits
while requiring identical source, root and configuration revisions. They publish
the completed certificate and remain ineligible until the readiness callback has
installed full journal coverage. Manual, flat and lexical builds retain their
strict source policy. Memory, construction and freshness budgets are unchanged.

Background certificates may sample stable physical source state during unrelated
Raft apply traffic. They cannot authorize public query results. A separate
controlled apply pause reproduced an exception from `vectorIndexStatus`; status
now reports `STALE` while the public applied watermark is behind, and reports
`READY` only after the same source, apply and journal checks used for queries.
The test also proves that ANN requests still time out rather than cross that
paused apply boundary. Actual vector edits during construction still invalidate
the graph and require reconstruction.

The public API fixture now records bounded, redacted engine startup diagnostics.
On Windows it uses the existing owned-engine CLI shutdown event to exercise
graceful termination. The native Windows diagnostic identified the accounts-file
POSIX mode check as the startup refusal; an unjoined memory monitor then masked
the refusal with fatal exit 70. The follow-up checks the opened credentials file
using native Windows ownership/ACLs or POSIX descriptor ownership/mode. It rejects
links/reparse files, non-regular input, broad access and input exceeding 1 MiB.
Windows SYSTEM/local administrators may retain host-management access. Ordinary
users/groups may not. Operators must make the file private; the reader never
changes its permissions. POSIX credentials must belong to the effective user.

The monitor now has scope-bound cleanup on startup refusal and exceptions.
The fixture installs a current-user Windows ACL and verifies a missing accounts
file exits cleanly with code 1, preserving the existing account roles and auth.
New reader tests exercise private input, broad-access refusal, null Windows ACLs,
invalid file types and both sides of the size bound. Malformed credential JSON
uses a generic diagnostic; parser input excerpts must not expose passwords.
These changes do not affect ANN algorithms,
WAL/LSM formats or acknowledgements. Latest platform checks passed as recorded
above; preceding Windows failures remain failures in their historical scope.

## Incremental prefix-progress follow-up

Focused ARM64 diagnostics reproduced the mixed-write failure on repetition four
after three passes. Immediately after failure the index was `STALE`, generation
38, with Raft commit and applied index both 91. Resource/capacity failure was not
reported. The precise cause of that native request failure remains unqualified.

A separate deterministic regression confirmed a maintenance liveness defect:
every resolution of one ID creates a later committed change to another ID. The
old worker repeatedly discards the same resolved prefix and cannot catch up.
The new complete-source path consumes bounded resolved prefixes and processes
later journal entries in subsequent batches. Query eligibility remains strict:
no prefix is public, root/configuration and version regression remain fenced,
and READY requires a stable final certificate and full journal coverage. Manual
sources retain their original strict policy. Freshness, memory and time budgets
are unchanged. Tests pause the next batch and verify that neither current nor
retained old certificates acquire the partial generation, then verify both final
IDs and negative dot-product distances. This first prefix checkpoint was not
sufficient to resolve the ARM64 request failure. Its baseline and failed native
results remain retained; the later wake-up candidate has its own qualification.

The prefix change passed the complete local checkpoint/Community suites and
selected ASan/UBSan/TSan tests, but its repeated ARM64 API run still failed on
repetition five after four passes. Immediately collected status was already
READY, with Raft commit/applied 107. That failure is retained and is not resolved
by the liveness test. A subsequent scheduling follow-up lets an ineligible query
coalesce a wake-up hint for existing maintenance instead of waiting for its
100 ms idle poll. It stores no caller context, cannot start/rebuild an index or
revive a failed worker, and leaves admission, coverage, freshness and request
deadlines unchanged. Local unit/API checks and broader repeated native
qualification subsequently passed for the wake-up candidate recorded above.

## Idle SDK connections

An independently reproduced Python/Java issue could reuse a connection already
closed by the server's idle timeout, or read a queued idle-error frame as the
next response. Python now retires observably expired idle sockets before dispatch.
Java probes leases idle for at least one second outside the pool lock, bounded
by the request deadline. Healthy TCP/TLS reuse and original public options remain.
No sent command is replayed; a close racing a send still produces an explicit
unknown-outcome error. Both EOF and queued-error cases are tested over TCP/TLS,
with exactly one transmitted write. This SDK change does not alter the qualified
engine tree or authoritative records.

## Readiness limits

Production readiness remains **INCOMPLETE**. Short tests cannot replace the
eight-hour stability gate, independent review of the exact release candidate,
physical-power qualification, or stable platform signing/install evidence.
Resource exhaustion, unavailable generations, real mutation lag, cancellation and
query deadlines may still return explicit errors; this change must never turn
them into stale or incomplete successful results. The earlier failed load run
must remain disclosed alongside new results.
