# Reproducing the Linux mixed-load qualification

This disposable engine/API profile tests one dense 1M GloVe-25 cosine space,
100,000 documents, and valid PNG/WAV/MP4 files. It is not a PostgreSQL/Qdrant
comparison or a production-readiness certificate. Timings depend on hardware,
page cache, workload and other host activity; identical results are not promised.

Use a clean source checkout and an engine built from that exact commit. Published
RC.2 packages contain earlier code and do not include these unreleased fixes.
The runner never connects to an existing service. It creates its own authenticated
TLS engine, uses WAL/fsync/flush/checksums, and SIGKILLs only that child during
recovery testing. Use a development host and an empty output directory.

The fixed Linux profile requires CPUs 0–5, at least 8 GiB available RAM at start,
and sufficient scratch disk (at least 15 GiB remains free during the run).
These are qualification headroom requirements, not PacificDB minimum deployment
requirements. The engine uses CPUs 0–3; the example pins the client to 4–5.
Resource guards stop the attempt on excessive engine PSS, disk use or low host
memory. Five-second samples can miss shorter peaks.

## Inputs and execution

Use Python 3.11 or newer for these qualification tools. Install normal native
build dependencies plus Python `numpy`, `psutil`, `h5py`
and `threadpoolctl`. OpenSSL and Linux `taskset` are required. Download the
unmodified public [GloVe-25 HDF5 corpus](https://ann-benchmarks.com/glove-25-angular.hdf5)
and prepare the checksum-frozen inputs with the existing tool:

```sh
python3 scripts/prepare-community-benchmark.py \
  --source /scratch/glove-25-angular.hdf5 \
  --publication /scratch/pacificdb-inputs
```

The tool verifies the original corpus, query selection, vectors and independent
reference checksums. Use its documented dependency versions if preparation does
not reproduce the frozen hashes; do not remove checksum checks.

From a clean checkout, build the matching engine and generate image/audio fixtures:

```sh
cmake -S engine -B build-load -DCMAKE_BUILD_TYPE=Release
cmake --build build-load -j2
python3 scripts/qualify-vector-mixed-load.py \
  --engine build-load/db_engine --expected-commit "$(git rev-parse HEAD)" \
  --dataset /scratch/pacificdb-inputs/data \
  --fixtures /scratch/pacificdb-media --root /scratch/pacificdb-load-new \
  --make-fixtures
```

Add a valid `test-video.mp4` to the fixture directory. For example, if FFmpeg is
installed, generate a deterministic test pattern with its MPEG-4 encoder:

```sh
ffmpeg -f lavfi -i 'testsrc2=size=320x240:rate=10' -t 3 \
  -c:v mpeg4 /scratch/pacificdb-media/test-video.mp4
taskset -c 4-5 python3 scripts/qualify-vector-mixed-load.py \
  --engine build-load/db_engine --expected-commit "$(git rev-parse HEAD)" \
  --dataset /scratch/pacificdb-inputs/data \
  --fixtures /scratch/pacificdb-media --root /scratch/pacificdb-load-new \
  --rows 1000000 --docs 100000 --seconds 1800 --ramp-seconds 60
```

Fixture hashes and sizes are recorded. Different file sizes change media latency
and throughput. Do not treat a different fixture profile as a matched comparison.
Build and runtime data must remain outside the tracked source tree or in ignored
build directories; the runner rejects a dirty checkout. Keep generated accounts,
TLS keys and database payloads private.

## Interpreting the evidence

The fresh profile seeds data, builds HNSW with M=16, ef_construction=200 and
ef_search=600, runs document/vector/media ramps at 1/8/32 clients, then a
30-minute mixed phase. Twelve mixed clients run four vector, seven document and
one media loop; document/vector loops are paced at 500 ms and media at 15 seconds.
ANN requests require the index and disable exact fallback; no failed query is
silently retried by the client. This is a mixed-workload latency observation,
not maximum QPS. Short index readiness after reuse of derived checkpoints is not
fresh graph construction time.

The runner verifies quiescent recall against exhaustive float64 cosine, mutated
records, media checksums, SIGKILL/restart, explicit derived-index reconstruction,
and post-restart document integrity. It opens a fresh control session at each
verification boundary instead of reusing a connection idle throughout the soak.
All 1M untouched vector payloads are not exhaustively fetched. Sparse, named,
hybrid, distributed and multi-host RF3 qualification are separate scopes.

Inspect `exit.json`, `phase-results.json`, `recall-*.json`, `integrity-*.json`,
`provenance.json`, and raw operation/resource logs. Only terminal `PASS` qualifies
the complete attempt. A passing timed phase followed by failed validation is
still a failed attempt. Retain every failure and never overwrite evidence.
At least 100 latency samples are required for p95 and 1,000 for p99.

The portable runner is a parameterized transcription of the exercised fresh
profile. Its CLI/compilation checks are recorded separately; the latest candidate
scale receipt used a backed-up existing corpus and separately recorded harness.
Do not attribute an unexecuted portable invocation to those measured results.
Thirty minutes does not satisfy eight-hour stability/Workbench, physical-power,
independent review, or stable signing/notarization gates.
