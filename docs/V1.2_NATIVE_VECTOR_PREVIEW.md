### Current additive query and status options

An explicitly selected HNSW index accepts wire `ef_search` (Node `efSearch`): a
positive integer no larger than that index's configured `ef_search`. Omission uses
the configured bound. This changes exploration for that request without mutating
the shared graph configuration. Results disclose the effective exploration bound.
It is invalid to pass zero, a fractional value or a value exceeding the bound.

Status includes `rebuild_required` and `maintenance_policy`. Incremental updates
retain bounded physical node history; exhaustion or lost change coverage requires
manual rebuild. A READY label alone is insufficient: query-time freshness and
authoritative result validation still apply and may return explicit lag/errors.

Release status: **INCOMPLETE**. These changes are uncommitted development work on
`v1.2`. This document describes the current implementation; the evidence section
separately records what has actually run. It does not authorize a release.

## Architecture and compatibility

Authoritative JSON dense, sparse-v1 and named vector records remain in existing
WAL/LSM storage. This checkpoint does not change their persistent representation,
Raft acknowledgement rules or historical numeric precision. Two derived dense
index algorithms are available in the standalone development preview:

- `flat`: packed float64 exact scan, cached norms and bounded top-K. It scans all
  eligible packed vectors and fetches only the winning authoritative documents.
- `hnsw`: hierarchical float32 derived graph, followed by authoritative document
  fetch and float64 score recomputation for the approximate candidate set.

Private generations are built on bounded workers. A completed generation is
published with a source certificate and retained by shared ownership. Every query
validates freshness before acquisition and after document retrieval. Any committed
source change makes the generation ineligible. Rebuilds release the previous
unserved generation on the worker; active readers keep their references and memory
charges. Insufficient memory while readers retain an old generation is an explicit
failure rather than unaccounted double allocation.

Collection drops cancel matching workers without joining them in committed apply.
Those workers destroy the derived graph, then finished worker reservations are
reaped on subsequent index admission. Dropping an index does not delete records.

The service limits active index workers, source reservations, derived allocations
and build time. Admission checks declared peak reservations against live process
memory and rechecks pressure during builds. This is conservative admission, not a
claim of complete process or tenant quota isolation. Two active index workers is
currently a process-wide limit. Multi-peer durable index catalog creation remains
blocked by its existing compatibility gate.

## Public preview

Set `PACIFICDB_VECTOR_PREVIEW_ENABLED=1` to opt in. It is disabled by default.
Existing `queryVector` requests without `index_name` keep the verified storage scan
path. The preview supports authenticated standalone actions:

- `createVectorIndex`: `collection`, `options` (including `name`, `algorithm`,
  `dimensions`, `metric`, resource bounds and optional `vector_name`/`text_field`).
- `vectorIndexStatus`, `rebuildVectorIndex`, `dropVectorIndex`: `collection`, `name`.
- `listVectorIndexes`: `collection`.
- `queryVector`: optional `index_name` and `require_index`.
- `queryHybrid`: `index_name`, `vector`, `text`, metric, candidate/ranking options.

Existing authentication, database ACL, tenant, namespace and strong-read gates
apply. Lifecycle operations are blocked until recovery completes. Writes require
leadership. Node, Python and Java expose corresponding named lifecycle and hybrid methods.
Python/Java options retain engine field names; Node maps camelCase query options.

`search_mode=exact` never uses HNSW. An eligible flat generation provides exact
ranking. `search_mode=ann` deliberately requests ANN; an exact plan is allowed only
by explicit fallback policy. `auto` can select the explicitly named eligible
index. The response reports the executed mode and any fallback. `require_index`
forbids a storage-scan fallback. Filters, unsupported read contexts and sparse
queries require the verified scan plan or an explicit eligibility error. A runtime
resource failure, timeout, cancellation or final freshness failure does not trigger
an unaccounted retry through another plan.

`VECTOR_HNSW_ENABLED=false` disables public HNSW creation, rebuild and execution;
it does not disable flat exact search. Legacy fallback policy is preserved.

`timeout_ms` is an optional integer from 0 through 3,600,000 on vector/hybrid
queries (Node: `timeoutMs`). It only shortens the operator deadline and propagates
through child rankers and fallback. Zero deliberately expires that request.
Daemon `MAX_QUERY_TIMEOUT_SEC` must be an integer from 1 through 86,400. Invalid
values are rejected before storage/recovery starts. Previously zero could time out
internal Raft visibility checks repeatedly; the failing fixture logs are retained.

Example (development, standalone):

```js
await client.createVectorIndex('vectors', {
  name: 'dense', algorithm: 'flat', dimensions: 25, metric: 'cosine',
  max_elements: 1000000, max_scan_rows: 1000001,
  max_source_bytes: 536870912, max_index_bytes: 536870912
});
// Poll vectorIndexStatus until READY; handle FAILED/STALE explicitly.
await client.queryVector('vectors', query, {
  indexName: 'dense', searchMode: 'exact', requireIndex: true, timeoutMs: 1000
});
```

A restart reconstructs no graph synchronously: durable definitions remain and
status is ABSENT until an explicit background rebuild. Snapshot restore and source
mutation invalidate old generations. Freshness is conservative: global committed
visibility and catalog changes can also require rebuilds after unrelated writes.
This makes the preview unsuitable for claiming continuous low-latency ANN under
arbitrary write traffic. Incremental committed maintenance is still incomplete.

production-readiness or universal performance superiority claim is supported.

## Completed public performance replay

The matched NVMe/ext4 replay passed three rounds of 100 held-out GloVe-25 queries
against 1M vectors. Median of round p50s: packed exact **36.61 ms**, PostgreSQL exact
**73.65 ms** (2.01× ratio), pgvector HNSW **2.11 ms** at Recall@10 0.981. Both exact
paths matched independent IDs with Recall@10 1.0. Flat source/build median 8.85 s;
flat allocation 298.0 MiB, sampled whole-run PacificDB PSS peak 703.3 MiB. Public
PacificDB ANN was not measured. The result applies to eligible static generations,
not arbitrary write traffic or production capacity.

for workload, raw evidence, memory/build tradeoffs and all incomplete release gates.
