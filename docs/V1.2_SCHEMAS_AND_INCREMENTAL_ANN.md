Current Community scope: [standalone candidate and benchmark contract](V1.2_COMMUNITY_SCOPE.md). The [latest-version benchmark](v1.2-evidence/community-official-20261031/STATUS.md) is in progress; earlier measurements remain revision-scoped.

## A. Implementation

### Immutable, enforced collection schemas

The opt-in standalone `createCollection` request accepts `vector_schema`:

```json
{
  "default": {"kind":"dense", "dimensions":2, "metric":"dot", "required":true},
  "named": {
    "image": {"kind":"dense", "dimensions":768, "metric":"cosine"},
    "terms": {"kind":"sparse", "dimensions":1000000, "metric":"dot", "required":true}
  },
  "allow_unconfigured": false,
  "format_version": 1
}
```

Each declared space has a dimension, dense/sparse kind, metric, explicit float64
precision and required/missing behavior. Sparse values retain the sorted-unique,
finite `sparse-v1` format. Named space count and aggregate numeric values are
bounded. Schema updates on an existing collection are refused; existing schema-less
collections retain their old behavior. Online schema migration is not implemented.

Definitions remain in the existing `db.meta` collection entry and its committed
CREATE_COLLECTION command. The engine publishes them atomically and synchronizes
the collection marker, metadata and directory links on POSIX. Later ordinary
collection/ACL edits in a schema-bearing database also use durable publication.
An in-memory immutable registry is a cache rebuilt from metadata at startup and
snapshot activation, not a second authoritative store.

Validation occurs before consensus for inserts, batch inserts and update post-images,
and at LSM put/batch/replay boundaries. Queries and indexes must match the declared
space. Trusted replicated deletes use an explicit tombstone intent; ordinary writes
cannot bypass required fields by selecting that intent. DELETE WAL semantics are
preserved for trusted tombstones. Per-database leases order DDL against concurrent
writes through acknowledgement, while independent writes share the lease. Trusted
committed apply bypasses the submitting client's lease to avoid a consensus/apply
deadlock. No graph work executes in those leases or acknowledgement callbacks.

Node: `createCollection(name, {vectorSchema})`; Python:
`create_collection(name, vector_schema=...)`; Java:
`createCollection(name, schemaMap)`. Existing signatures still work.
`PACIFICDB_VECTOR_PREVIEW_ENABLED=1` is required for public schema creation.
Multi-peer schema creation remains gated until mixed-version/downgrade and peer
capability guarantees are implemented and qualified.

### Incremental HNSW preview

Set `maintenance: "incremental"` on a HNSW-only index over a configured dense space:

```js
await client.createCollection('vectors', {
  vectorSchema: { default: { dimensions: 2, metric: 'dot', required: true } }
});
await client.createVectorIndex('vectors', {
  name: 'ann', dimensions: 2, metric: 'dot', maintenance: 'incremental',
  max_elements: 2000000, max_source_bytes: 268435456,
  max_index_bytes: 1073741824
});
// Poll until READY; handle STALE/FAILED explicitly.
await client.queryVector('vectors', query, {
  indexName: 'ann', requireIndex: true, searchMode: 'ann',
  allowExactFallback: false
});
```

The mode is additive; manual rebuild remains the default. Flat exact and lexical
hybrid indexes retain their existing mutation invalidation/rebuild behavior.
Incremental sparse/flat/lexical maintenance is not claimed.

LSM single/batch puts and deletes record changed IDs into subscribed, replica-local
bounded journals. Root recovery/restore and collection drop invalidate history.
The journal contains no vectors or second WAL. Missing history, allocation failure,
overflow or unsupported IDs produce an explicit coverage gap requiring a rebuild.
There are at most 64 subscriptions, 4096 retained changes per collection and 1 MiB
of journal allocation per subscription, within a shared 64 MiB allocation cap.
These are journal allocation bounds; they do not qualify complete process RSS or
tenant quotas. Expired subscriptions are pruned on new subscription admission.

The existing index worker consumes bounded batches, resolves changed IDs through
committed authoritative reads and applies HNSW replacement/deletion. It does not
build a graph in Raft acknowledgement. Duplicate IDs in a batch are coalesced;
metadata-only edits do not append replacement graph nodes. READY publication
requires covered history and a stable source certificate. A concurrent query
revalidates after authoritative payload fetch. During lag it gets an explicit
eligibility error or the declared full exact fallback, never a partial ranking
presented as exact. Pending/uncommitted source rows cannot silently be omitted
from an initial eligible incremental generation.

Full-build publication retains the prior immutable-generation behavior. The
opt-in incremental preview mutates the graph under its per-index shared mutex and
publishes new immutable certificate metadata. It does **not** provide a physically
immutable graph snapshot to retained readers. Those readers must perform the
existing final authoritative-certificate validation. The stricter immutable-graph
generation acceptance criterion therefore remains **INCOMPLETE**; a persistent
copy-on-write graph or independently qualified immutable base-plus-delta design is
still required before claiming that production criterion.

HNSW replacements append a node and tombstone the old node. Tombstones remain
navigation bridges and never final hits. The live-ID map contains one current node
per ID. `max_elements` bounds **physical history**, including tombstones; reserve
headroom for updates. Reaching that or an allocation/time bound fails eligibility
and requires a rebuild. Automatic graph compaction is **INCOMPLETE**; sustained
unbounded update traffic is not production-qualified. Replica-local graphs need
not be byte-identical.

## B. Correctness and recovery fixes found by tests

1. Required-vector validation initially rejected replicated tombstones on the
   shared put path. Explicit trusted tombstone intent repairs that integration.
2. A standalone crash could leave schema DDL in its durable log suffix until the
   next write, whose validation had already run. Startup now commits/applies a
   no-op fence for a one-member durable suffix before opening client sockets.
   It refuses the listener on failure. This does not commit arbitrary multi-peer
   follower tails.
3. Failed committed apply spun continuously and logged `payload.dump(512)`, where
   512 was indentation, not a length limit. Failure output now summarizes bounded
   identifiers and the worker retries at most once per 250 ms. Failed progress
   remains unchanged; the injected-failure test proves recovery after restart.
4. Later metadata edits could overwrite a schema-bearing file using older write
   paths. They now preserve atomic durable publication in that database.

The original failures, corrected fixture mistakes and raw attempts are retained.
The first intermediate full regression attempt failed the opaque snapshot bundle
case; schema discovery now preserves low-level opaque artifacts that do not
represent an active collection database. Actual malformed engine metadata remains
an error. No failing assertion was removed or disabled.

## C. Files and integration points

- `vector_schema.hpp/.cpp`, `vector_schema_lease.hpp`: validation, cached schemas,
  immutable creation constraints, metadata durability and DDL/write ordering.
- `database_engine.hpp/.cpp`, `lsm.hpp/.cpp`, `server.cpp`, `main.cpp`,
  `raft_core.cpp`: pre-commit/post-image/replay validation, trusted tombstones,
  optional raw latest-row discovery, journals, startup fence and retry bounds.
- `vector_change_journal.hpp/.cpp`, `vector_change_registry.hpp/.cpp`: bounded
  history, subscriptions, explicit gaps, visibility gates and root invalidation.
- `read_cache.hpp`, `hnsw_index.cpp`: incremental replacement/deletion and live-hit
  traversal with physical node/resource bounds.
- `vector_index_generation.hpp/.cpp`, `vector_index_incremental.cpp`, native service,
  native integration and vector catalog: reuse existing workers, source anchors,
  asynchronous mutation application and eligible-generation publication.
- Node/Python/Java client creation overloads and integration clients: optional schemas.
- New schema/storage, journal, HNSW mutation and worker tests; public schema,
  incremental API, crash-publication and bounded-retry scripts; checkpoint runner.

## E. Release blockers

**INCOMPLETE:** physically immutable incremental graph generations;
mixed-version schema/catalog capability and downgrade protection;
real shard ownership/data transfer and complete distributed query routing;
automatic graph compaction and long-duration maintenance; high-dimensional and
filtered mixed workloads at scale; full RSS/tenant/global resource qualification;
complete packaging, upgrade, security and recovery matrices. Disk/quantization
features remain separately gated. The requested sustained-load qualification is
still required here despite the older general release audit listing its historical
long-duration gate as EXCLUDED. That exclusion is not counted as completion of
this request. Flat/hybrid incremental maintenance remains
unsupported. Public multi-peer schema/catalog operations remain gated.

`ShardManager::migrateShard` currently changes `primaryHost`/status and persists a
map. It does not copy records or transfer a committed ownership fence. The engine
has one RaftCore replication group, not qualified independent shard replica groups.
Adding a top-K merge or fan-out over that metadata would not prove distributed
completeness. That missing storage/ownership protocol must be implemented and
qualified before this release criterion can pass.

The earlier [public benchmark bundle](PacificDB-v1.2-development-native-vector-benchmark-20261030.zip)
remains attached to its own frozen daemon/source. This checkpoint does not
retroactively qualify that binary or establish production ANN superiority.

## H. Reproduction

Use clean, separate Release and destructive-test builds with the captured compiler
and dependencies. The toolchain file in evidence documents the local dependency
prefix; adapt those paths for another machine. Keep failpoint runs on disposable
roots. Each checkpoint evidence directory must be empty initially.

```bash
cmake -S engine -B build-v1.2-next -DCMAKE_BUILD_TYPE=Release \
  -DPACIFICDB_ENGINE_VERSION=1.2.0-dev
cmake --build build-v1.2-next -j2
cmake -S engine -B build-v1.2-next-failpoints -DCMAKE_BUILD_TYPE=Release \
  -DPACIFICDB_ENGINE_VERSION=1.2.0-dev -DPACIFICDB_ENABLE_TEST_FAILPOINTS=ON
cmake --build build-v1.2-next-failpoints -j2
python3 scripts/test-vector-checkpoint.py --build build-v1.2-next \
  --failpoint-build build-v1.2-next-failpoints --expected-version 1.2.0-dev \
  --evidence /path/to/empty-checkpoint-evidence

# Direct core scale qualification; not a public API benchmark.
build-v1.2-next/db_engine_hnsw_incremental_test 1000000 100 cosine
```

The public preview requires `PACIFICDB_VECTOR_PREVIEW_ENABLED=1`; this does not
remove the multi-peer capability gate. TSAN uses a separate build with
`-DENABLE_TSAN=ON`; the five targeted test names are in `tsan-results.json`.
The full source archive and compiler/configuration logs are retained with evidence.
