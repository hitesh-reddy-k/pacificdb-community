# PacificDB v1.2 Community: scoped candidate and benchmark protocol

This is an unpublished development candidate. The user has chosen a narrower
Community release scope; the earlier complete distributed-vector acceptance scope
is retained as future work, not falsely marked PASS.

## Required supported scope

- Standalone authoritative WAL/LSM dense, sparse and named vector records.
- Enforced immutable creation-time collection schemas; legacy schema-less behavior.
- Correct bounded exact search, metadata filtering and explicit resource failures.
- Derived HNSW lifecycle with safe source eligibility and manual rebuild/recovery.
- Validated per-index locking and final source validation are an acceptable
  concurrency strategy for this Community scope; physically immutable graph
  snapshots are not required by this scoped release contract.
- Explicit bounded physical history and documented manual maintenance. Automatic
  compaction is deferred; no unlimited-update-capacity promise is made.
- Existing document/media/authentication/SDK/WAL/LSM/RF3 flows remain supported and
  regression-tested. Unsupported clustered vector schema/catalog creation remains
  gated. Distributed sharded vector search is not advertised.
- Incremental HNSW is opt-in and is reported separately from static index results.
  Sparse/flat/lexical incremental maintenance is unsupported and explicitly errors
  or follows the declared complete exact fallback policy.

Correctness, durability, resource/isolation behavior, backup/recovery and upgrade
validation for the advertised scope remain required. Existing release audit policy
is not disabled. A reproducible project benchmark is not independent certification
or automatic production-release approval. No commit, push or external publication
is authorized by preparation of these local artifacts.

## Benchmark contract

The report is a self-run PacificDB project comparison prepared for company review.
It pins a complete candidate source archive, binary hashes, dependency versions,
compiler/configuration and raw records. PostgreSQL's official version policy and
pgvector tagged changelog identify PostgreSQL 18.6 and pgvector 0.8.7 as the stable
comparison baseline on 2026-10-31; PostgreSQL 19 RC is excluded from stable claims.
Sources: https://www.postgresql.org/support/versioning/ and
https://github.com/pgvector/pgvector/blob/v0.8.7/CHANGELOG.md .

Use disposable NVMe/ext4 data roots and random local ports. Never change running
application databases or benchmark source snapshots. Both systems retain fsync,
commit acknowledgement and crash recovery. Standalone is compared with standalone;
RF3 qualification is a separate test, not a latency comparison against one node.

Primary dataset: shared float32 GloVe-25 values, 10K/100K/1M rows. Independent
float64 exact references; queries held out from index tuning. Measure exact versus
exact and ANN versus ANN, full vector/document payloads, recall and cardinality.
Tune each ANN against the same recall target (>=0.95), then evaluate held-out queries.
Record build/source time, index parameters, warmups, raw per-query latencies,
serial/concurrent throughput, p50/p95/p99 only with declared sample counts, sampled
RSS/PSS, storage/WAL, shutdown and restart. Report query-plan verification and
fallbacks explicitly. Use matched data/settings, alternate measurement order and
retain every failure. No guarantee of outperforming pgvector is assumed.

The extended matrix covers fresh batch ingestion; update/delete visibility;
metadata-selective exact search; small higher-dimensional/multiple-metric cases;
sparse/named capability checks; concurrency and mixed mutation/search; restart and
crash recovery. Text/hybrid differences and unsupported features are labelled,
not treated as equivalent algorithms. Exhaustive combinations, actual power loss,
all hardware/OSes and multi-shard behavior cannot be inferred from this machine.
Any unexecuted workload is INCOMPLETE/BLOCKED, not PASS. The final report states
exactly which entries completed and provides source scripts and evidence.
