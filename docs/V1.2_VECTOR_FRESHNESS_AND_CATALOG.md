# Vector freshness and durable catalog integration

Verified freshness/catalog checkpoint; subsequent namespace-identity work has a separate gate. Public ANN remains gated;
the complete subsystem and release remain INCOMPLETE.

## A. Implementation

`vector_freshness.hpp` supplies process-local, composite certificates containing
root revision, collection revision and committed-visibility index. Root and
collection mutations have RAII active counters; capture refuses a certificate
while a relevant change is active. Counters use sequentially consistent atomics,
not an added storage mutex. A fixed 4,096-slot array bounds tracking memory. Hash
collisions conservatively invalidate unrelated indexes; they cannot grant false
freshness. Revision wrap poisons the slot rather than permitting certificate reuse.

`lsm.hpp/.cpp` integrate these guards immediately before authoritative memtable
mutation in put/putMany/delete and around collection drop. Initialization, WAL
replay and snapshot installation use root-wide guards. Failed root operations conservatively invalidate
indexes too. Nested restore guards remain ineligible until all guards leave.
Physical compaction does not change logical records and needs no new certificate.
Offline backups restore to a separately guarded target; opening that target runs
root initialization/recovery before any new in-memory generation can be eligible.
No WAL payload, fsync setting, persisted vector bytes or acknowledgement rule changed.

`vector_index_generation.hpp/.cpp` now use an optional composite certificate, not
an opaque scalar/hash. A changing source cannot start a generation. Before/after
certificate checks reject mutations during collection or construction. Consumers
must still recheck after authoritative candidate fetch; this is not historical MVCC.

`vector_index_catalog.hpp/.cpp` add a trusted internal catalog for validated HNSW
configuration. Definitions use ordinary tenant-owned documents in
`pacificdb_meta/vector_index_specs_v1`, with format_version=1, dimensions, field,
metric, M, construction/search exploration, node count and source-byte budget.
Unknown options and invalid values fail explicitly; no quantization is implied.
Authoritative vectors retain their legacy numeric encoding. The graph remains a
derived float32 representation only.

Definitions bind to the target collection incarnation and use unambiguous record
IDs. Drops/recreates cannot reattach old standalone definitions. Catalog listing
has a 4,096-row hard scan ceiling and fails rather than returning a partial list.
It does not initialize storage on reads. Configure/delete use existing mutation
paths; B-tree CREATE_INDEX handling is unchanged. Catalog methods are not exposed
as public RPCs yet and require router authorization before any future public use.

### Confirmed distributed prerequisite

Current CREATE_COLLECTION apply generates independent local collection IDs on
replicas. A leader-generated catalog definition bound to that ID would disappear
on other replicas or fail to identify a dropped/recreated namespace correctly.
Catalog operations therefore explicitly reject RF3 with
`vector_index_catalog_distributed_identity_unavailable`. A replicated collection
incarnation and mixed-version capability gate are required before this is enabled.
This dependency is not repaired by scanning records or trusting local metadata.

## Recovery lock-order defect and isolated repair

The new catalog replay test exposed a pre-existing potential deadlock under
ThreadSanitizer: collection writes hold a collection lock then append to WAL,
whereas recovery held the WAL append mutex while acquiring the collection lock.
The original failing sanitizer log is retained; no warning was suppressed.

`wal.hpp/.cpp` add `scanRecovery`, which reserves an idle logical log using a
single atomic admission word (exclusive recovery bit or active operation count).
Recovery callbacks execute without holding the append mutex. Normal append,
queued-write lifetime, force-flush, passive scan, clear and reclamation participate
in this per-log admission. There is no added global lock, spool file or new WAL
format. Recovery admission fails if work is already admitted; it cannot revoke
that work. An operation attempted during exclusive recovery fails explicitly with
`wal_recovery_in_progress`, before changing buffered entries or bytes. Admission
is released on normal return and callback exceptions.

LSM replay uses this new API; existing bounded replay flushes and deferred WAL
reclamation remain. Ordinary `WAL::scan` retains its passive-scan locking semantics
and must not be used for callbacks that acquire storage locks or mutate that log.
The new API is for recovery, not a live query or an uncoordinated online restore.

`wal_recovery_admission_test.cpp` passed normally and under ThreadSanitizer:
conflicting writes, clear, fsync and reclaim fail explicitly during recovery;
blocked maintenance leaves an admitted writer able to finish; callback failure
releases admission; the final checksum-validated log contains all four expected
records with consecutive LSNs. Full crash/restart/regression gates are still
required because this repair touches a shared durability subsystem.
